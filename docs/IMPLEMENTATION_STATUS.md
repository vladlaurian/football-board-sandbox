# Implementation status — checklist

Single source of truth for **what's built vs. not**. A new chat should read
this file first, before assuming anything about mechanic status from memory
or from other docs' prose (those go stale after remote work ships).

**When a mechanic ships:** check its box, add the version and a one-line
pointer to the engine file, and update its row in the "Not implemented" table
if it unblocked anything downstream. Do not delete finished rows — this file
is a running log, not just a snapshot.

Checked at the moment `completePass` would otherwise finish an uncontested pass (nothing can have moved since `PASS_ROUTE_CONFIRMED`, since `state.actionResolution` blocks every other command meanwhile — so this *is* "the exact moment the ball is played", no separate frozen snapshot needed). Tests the confirmed `targetPlayerId` recipient against the 3 real conditions (opponent's half, nearer goal than the ball, nearer goal than the second-last opponent — goalkeeper included in that ranking) using one direction-agnostic "advancement" helper for both teams. An intercepted pass (including a direct hit and the goalkeeper-blocks-route case) never reaches the check at all — only an uncontested completion to the intended teammate does. An offside result never completes the pass — the ball stays exactly where it was, `state.pendingRestartResult` records `{type: "indirectFreeKick", team: <opponent of the passer>, spot: <the offside player's own unmoved position>}`, and a shared result screen (`actionResolution.kind === "offside", status: "result-display"` — same shape Build 2's own claim hooks use, one shared screen and one shared `OFFSIDE_RESTART_CONFIRMED` handler cover both) shows before proceeding into the Indirect Free Kick's own restart setup — see the Direct/Indirect Free Kick row below.
- [x] **Offside — Build 2, Through Ball / Lofted Through Ball** (`src/engine/offsidePositionRules.mjs`'s `computeOffsideWatch`/`resolveOffsideWatchClaim`, wired into `throughBallRules.mjs`'s `commitThroughBall`, `loftedThroughBallRules.mjs`'s `resolveLoftedThroughBall`, and the claim side in `normalMoveRules.mjs`, `bonusMoveRules.mjs`, `threeTwoMoveRules.mjs`) — both mechanics' own "recovery race" only ever decides attacker-team-vs-defender-team, never which specific attacker eventually reaches the now-loose ball (that's resolved later by real gameplay — an ordinary Move, a Bonus Move, or a 3/2 resolution, the exact three ways docs section 6 says a player can "reach it"). The instant the attacking team wins that race, `state.offsideWatch = { attackingTeam, flaggedPieceIds }` flags every attacking field piece (other than the passer) currently offside — not just the theoretically closest one. Whichever piece then lands on that loose ball first is checked against the watch: a flagged piece triggers the same frozen `actionResolution.kind === "offside"` result screen and `pendingRestartResult` Pass Build 1 already has (spot = the piece's own position at the moment it claims the ball, not its original offside position — matches real law: the offence is judged at the moment it's discovered, not when the ball was first played); anyone else claiming it first (flagged-team non-flagged attacker, or any defender) just spends the watch with no consequence. Confirmed live with the user: **the watch deliberately survives every turn/phase transition** — an attacker who can only close part of the distance before its own Speed runs out, then finishes the approach on a later turn once Speed refills, is still offside from the original pass; `state.offsideWatch` is a new canonical top-level field (`src/game/gameState.mjs`) explicitly never touched by `trackerPhaseRules.mjs`'s turn/phase resets. Group Move can't land on the ball at all (its own `GROUP_MOVE_BALL_DESTINATION` rejection), so it was never wired. Free Move is administrative/setup-only, not a live gameplay path, so it wasn't wired either.
- [x] **Offside movement-direction lock** (house rule, not IFAB law — `GAMEPLAY_RULES_FOUNDATIONS.md` section 6, confirmed live with the user) — `src/engine/offsidePositionRules.mjs` (`isPieceInOffsidePosition`, the shared live position check, also now used by the Build 1 row above), wired into `src/engine/normalMoveRules.mjs`'s `evaluateNormalMove`/`commitNormalMove`. In a turn-based game a player who starts a movement session already offside could otherwise retreat onside, receive a pass mid-session (the pass never touches this player's own movement state, so nothing here stops it), then reverse and break away alone in the same session — unconditionally defeating any defensive offside trap, a problem real football doesn't have because it has no equivalent of "no reaction-time cost." Checked once, at a fresh session's first commit only (no `axis` yet committed this session): if the piece is offside at that instant, `movementStateByPieceId` locks `directionLocked: true` to whichever direction the first hop takes — reusing the exact flag/mechanism Three-Two Move's own bonus continuation already sets, the two are compatible since neither cares why the other set it. A locked player may still finish moving that direction, receive a pass, build up play, or shoot; only reversing axis direction within that same session is rejected (`reason: "offside-direction"`, kept distinct from Three-Two's own `reason: "direction"` since `applyGameCommand` strips a rejection down to `{accepted, reason}` before the UI ever sees it — there is no `current.threeTwoUsed` to branch on that late). **Scope**: wired into both Normal Move and Bonus Move (`src/engine/bonusMoveRules.mjs`'s own local `movementState()` normalizer was fixed to carry `directionLocked`/`direction` through commits, which it silently dropped before). Free Move is administrative/setup-only (no Speed budget, no team-turn gating, not a live gameplay escape route) — not wired. Group Move moves each piece exactly once per activation (blocked from a second segment by its own `GROUP_MOVE_PIECE_ALREADY_MOVED` check), so it cannot reverse within one session regardless — not wired either.
- [x] **Tackling — Build 1 only, normal defensive action** (`src/engine/tacklingRules.mjs`) — **the design here supersedes `TACKLING_RULES.md`'s original text in several places; the doc itself has only had a partial rewrite pass (see the note at its top) — trust this row and the code over the doc's remaining stale prose.** Eligibility: frozen at defense-phase start (`trackerPhaseRules.mjs`), the *only* condition is the ball carrier standing inside the defender's own defensive area at that instant — the original "3 orthogonal / 2 diagonal" distance route no longer exists as a separate condition. Execution: every attempt auto-walks the defender toward the carrier along whichever single legal straight/diagonal axis reaches its proximity fastest (no distance cap), landing adjacent before the roll ever opens; if every legal axis is blocked by a body, or the carrier is no longer inside the defender's defensive area (checked fresh, since the defender may have repositioned since the frozen snapshot), a no-cost canonical notice opens instead (`TACKLING_NOTICE_ACKNOWLEDGED` to close it) — neither consumes any Tracker/personal/team action. Once the roll truly opens, the Tracker/personal action is consumed exactly like every other mechanic. Roll: D20 + Tackling vs Ball Control, resolved in three canonical stages mirroring Shot exactly (`TACKLING_STARTED`/`GAMEPLAY_ROLL_SUBMITTED` roll → 1s hold → `TACKLING_RESOLUTION_DUE` computes the result for display only → `TACKLING_CONSEQUENCE_DUE` on Continue actually applies it to the board). Natural 20 always succeeds; Natural 1 always fails and is never reclassified as equality. Free Kick / Yellow Card / Red Card are three independent Rule Set thresholds (1-7): at 1 each checks the natural roll directly, from 2 up each checks the total instead (after the Tackling bonus) — Red always wins a Yellow/Red overlap. Equality is a Rule Set band (1-5, always on total) below Ball Control, configurable to either "Tackling succeeds" or "ball out of play" (Throw-in/Corner, possession always to the attacking team, wins any overlap with a fault band). A successful Tackling needs no extra placement step — the defender is already adjacent from the pre-roll auto-walk. Inactivity: the 3 triggers in `GAMEPLAY_RULES_FOUNDATIONS.md` section 3, plus a 4th confirmed by the user — any stoppage (a foul, or equality's ball-out) ends it immediately, so a fouling/stopped defender is never frozen through the outcome that follows. Cards are recorded canonically (`state.disciplinaryCards`) with no gameplay effect. A foul outside the penalty area now proceeds (via Continue) straight into a Direct Free Kick's own restart setup — see the row below; a foul inside the box (Penalty, not yet built) or equality's out-of-play (Throw-in, not yet built) still freeze the result screen with no Continue, confirmed: any outcome needing a restart type this build still cannot execute stays frozen. UI: the `TACKLING` action button (`matchPresentationSelectors.mjs`) dispatches it for an eligible defender; the roll reuses the existing generic dice-roll button; the notice/result screens reuse the existing `ActionResultModal`/`RollPromptCard` system (same one Shot uses), in English, each its own Undo/Redo-able Timeline step. **Not done — see the matching rows below**: sections 1.2/1.3 reactive forms; ties among several equally-closest cells (not reachable in Build 1's design, since the auto-walk always resolves to one specific nearest axis-reachable cell, but noted in case a future reactive form reintroduces the case); Shot's own `goalKickInterval`/equality are not aligned to this same "after bonus" pattern (noted for later, not touched).
- [x] **Direct Free Kick / Indirect Free Kick** (`FINALISATION_AND_RESTARTS_RULES.md` section 7) — the shared wall/reposition/executor/execution-gate restart engine (`src/engine/restartSetupRules.mjs`, `gameEngine.mjs`'s `RESTART_EXECUTION_ACTION_FAMILIES`), the Lofted Through Ball threshold-18 override, and Shot's own body/origin-relaxed contract for a direct free kick shot were already written and generic — this build was purely wiring the two triggers into it, same pattern as Corner/Goal Kick. **Direct**: `tacklingRules.mjs`'s foul consequence computes `result.restartType` ("penalty" if inside the box, else "freeKick") once, in `resolveTacklingResult`; `applyTacklingConsequence`'s freeze gate now only withholds Continue for a penalty-area foul (Penalty not built) or equality's out-of-play (Throw-in not built) — an outside-the-box foul's Continue calls `buildRestartSetup(ruleSet, "freeKickDirect", attackingTeam, foulSpot)` directly, same as Corner/Goal Kick's own consequence functions. **Indirect**: a new shared `confirmOffsideRestart` (`src/engine/offsidePositionRules.mjs`, dispatched via the new `OFFSIDE_RESTART_CONFIRMED` command) reads `state.pendingRestartResult` (`{team, spot}`, the same shape all 4 offside-detection call sites already wrote) and calls `buildRestartSetup(ruleSet, "freeKickIndirect", team, spot)` — one handler covers Pass Build 1 and Build 2's Through Ball/Lofted Through Ball claim hooks alike, since Pass Build 1's own offside screen was normalized to the same `actionResolution.kind === "offside"` shape Build 2 already used (previously `kind:"pass", status:"offside-result-display"` — a pre-existing inconsistency, fixed in the same pass). Cross is not in `freeKickDirect`'s `availableActions` (Crossing itself isn't built, matching Corner's own gap). **v21.1.0**: both trigger functions now also move the ball piece itself to the restart spot (`moveBallTo`/`clearCellForPlacement`, previously only `restartSetup.ballCell` was set, the live board never updated); the wall step is now its own position+length screen (`RESTART_WALL_POSITION_SET`) before player selection, with a "No Wall" option and a live board highlight, shared by Corner too; a defending player within the illegal distance (5 orthogonal/4 diagonal) must reposition first and can never be repositioned back into that zone (`illegalDistanceDefenderIds`, mirrors Goal Kick's own box rule); a reposition that would extend the wall's own fixed line opens a Yes/No confirm (`RESTART_WALL_CONTINUATION_CONFIRMED`/`DECLINED`) instead of silently joining it; extra reposition moves from an illegal-distance/box overflow are now granted symmetrically to both sides, computed upfront; Inspector action buttons are disabled (not just rejected after a click) when not in the executing restart's own `availableActions`.
- [x] **Goalkeeper Retains — untracked reposition** (`src/engine/gkRepositionRules.mjs`, v21.1.0) — after a Goalkeeper Retains, an optional alternating reposition window (goalkeeper's own team first), using the same movement-legality primitives as Normal Move (`getMovementGeometry`, `diagonalCostForDistance`, `firstPlayerBlockingMovementPath`) but writing nothing to the Tracker — a parallel `state.gkReposition`/`gkRepositionMovementByPieceId`, never `movementStateByPieceId`. Rule-Set-configured move count per side (`actions.shot.goalkeeperRetainsReposition.count`, 0 disables the whole phase) and three independent trigger checkboxes (`afterFreeKick`, `afterCornerHeader` — inert, corner-header shots aren't built yet — `anyCatch`). Exactly one piece per turn (`GK_REPOSITION_PIECE_SELECTED` locks `activePieceId` until `GK_REPOSITION_TURN_ENDED`), and a piece used on any turn is retired for the rest of that whole phase, not just that turn — otherwise the same piece could chain several turns' worth of Speed. Gates every other command (Free Move/Free Ball stay exempt, same testing-engine convenience as restartSetup's own gate) until it closes, always resolving before any pending Bonus Action or ordinary play resumes.

## Cross-check discipline

Before trusting any other doc's prose about whether X is implemented, verify
against actual code (`grep -rl` for the expected engine filename or exported
function, or check `docs/CHANGELOG.md` for a shipped version). This file
itself needs the same discipline — if you find it's drifted from the code,
fix it in the same pass, the same way `GAME_ENGINE_MIGRATION_PLAN.md`,
`GAMEPLAY_RULES_FOUNDATIONS.md`, `TEAM_COMPOSITION_AND_FORMATIONS.md` and
`ARCHITECTURE_DECISIONS.md` had drifted before this file was created
